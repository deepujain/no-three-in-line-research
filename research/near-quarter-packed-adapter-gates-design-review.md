## Geometry and arithmetic

The proposed state represents the same near-quarter family as the frozen model: ordered quarter-turn four-orbits off both diagonals, followed by the same main-diagonal half-turn pairs, with the anti-diagonal and center absent. Sorting canonical coordinate tuples in the original order preserves orbit IDs and insertion order. A specialized read-only orbit view and minimal model mapping suffice for the existing `expand` and dual `check_candidate` code; weighted-line code would additionally need the omitted point-to-variable mapping and must not be called. Tests must compare the complete ordered map against the frozen oracle.

The secant invariant is exact: for a fresh unoccupied point p, a positive counter means some existing selected pair is collinear with p. Adding each new point increments the full maximal grid line with every earlier point exactly once, endpoints included. Thus valid point additions preserve the no-three-collinear property, and inverse operations restore the same counts. Row/column caps and orbit-family/type caps retain their existing meaning.

I independently checked the arithmetic without constructing an n79 model. At n79 the bounds are 1521 four-orbits, 39 diagonal pairs, 1560 IDs, 6162 stored incidences, 6241 cells and 158 selected points. Model arrays use 15,446 bytes, live geometry arrays/stacks 19,277, the stated permutations 3,278 and scratch 6,400, totaling 44,401 bytes for those representations. This excludes object overhead and transient/interpreter/verifier/guard memory and is not an RSS prediction. Individual-cell blocker counts are at most `C(158,2)=12403`, safely below 65536; coordinates, offsets, IDs and contributor counts also fit the checked two-byte unsigned representation. The 1,155,960 possible local pairs cannot be stored as a two-byte flat count and remain represented by two local indices.

These bounds depend on enforcing type caps, distinct occupancy and at most 158 transient points before mutation. Unsupported `array('H')` width is rejected. Overflow/underflow is a fatal consistency error that poisons the stage, never a search rejection or pruning argument.

## Transaction and integration obligations

The proposed point progress record is sufficient without a cell journal. Its previous-point index records fully processed pair lines; its cell index records exactly the completed prefix of the current line. Before commit, cancellation reverses that prefix and then the complete earlier lines, leaving point occupancy and row/column metadata untouched. Orbit failure then removes all fully committed points back to the orbit's entry length. Whole-batch rollback composes these transactions across at most two orbits. Implementations must update progress consistently with each mutation and place all stop checks at the specified boundaries; an unexpected inverse fault poisons the state and forbids saving.

Inverse operations must finish despite cancellation. A nonthrowing poll latches the stop, the inverse reaches its coherent entry/parent state, and the core commits the corresponding pop/frame transition before propagating the stop. Successful insertion that is interrupted before its frontier commit instead rolls back. Preallocated successor/child metadata and a final check before logical commits prevent cancelled scratch scans from producing counted events. Fault tests must include the last cell update, line transitions and the interval before point/orbit metadata commit, along with both batch positions. The snapshot must include zeroed unused stack slots, lengths/type counts and poison/pending flags, so private replay comparison cannot overlook latent mutable state.

The scan rewrite preserves the mathematical row policy only if the retained one/two-weight counts reproduce the exact contributor count, optimistic reachability and declared order. With counts c1/c2 and r remaining orbits, the domain size is `c1+c2` and the optimistic sum is `2*min(c2,r)+min(c1,max(0,r-c2))`. The chosen-row candidate buffer must follow the existing orbit declaration. No new global-ID restriction or cached depth-dependent domain is introduced.

Closed literal adapter selection, separate import-time source bundles and the existing adapter identity tag are appropriate. Adapter2 remains first-event mode only; adapter1 remains hard tiny. Source changes intentionally invalidate old source-bound replay rather than migrating historical checkpoints. Exact phase/cursor transitions, strict wire bounds, trusted external content/parent/chain identities, private reconstruction and full live/replayed snapshot comparison remain required. An interrupted or poisoned reconstruction yields no adopted core and cannot consume an accepted parent.

## Validation and measured gates

The staged sequence is appropriate. First, n3/n5/n7 tests compare all tiny subsets/extensions with the independent determinant oracle and frozen state, ordered maps, accepted/rejected snapshots, full undo and leaves. Exhaustive representative cell-boundary fault injection and poison/save refusal then validate the transaction contract. Next, integrated adapter2 tiny phase roundtrips, one-node continuation, declaration reversals, repeated leaf acknowledgment, malformed authority and publication faults must match adapter1 in the same first-event mode. The abstract twelve-leaf quota fixture remains control-flow evidence only.

After source approval, the Lead separately schedules and reviews actual-host tiny lifecycle/receipt gates, one fixed n71 witness insertion/dual-check/undo gate, the n9 25-node pilot, the n79 construction/hash/diagonal push-pop preflight, and only then the proposed single-node n79 cost stage. The unchanged helper and proposed deadlines/RSS caps retain the existing acceptance policy. Cleanup and reconstruction count as physical work, with separate logical counters and phase timings. Sampled RSS and cooperative Python/filesystem operations do not create a hard real-time guarantee. Failed, restore-limited, source-changed or incompletely cleaned stages cannot advance acceptance, retry unchanged automatically or raise caps. Future witness/report durability and supervisor acceptance require separate implementation review. No current runtime or performance claim follows from this design approval.
