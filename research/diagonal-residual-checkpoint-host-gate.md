There is no shared dispatcher or chain route.

The script makes exactly two success-path guard invocations for each of n3 and n5: a fresh one-node start followed by an explicit hash-pinned resume with a 1,000-node quota. It requires total logical nodes 19 and 192, respectively, all declared slices exhausted, exact residual format/order/prune-policy/source identities, linked predecessor digests, positive helper RSS and cleanup samples, no monitor or cleanup errors, clean owned-tree cleanup, and both helper and invocation elapsed limits passing. Every invocation requests ten seconds and 256 MiB from the unmodified helper through the standalone guard. No result is accepted merely because the worker exited. There are no retries, cap increases, alternate backends or additional numerical cases.

All emitted success-path certificates are independently rerun through both frozen integer verifiers by the tiny gate driver, and checked for exact point count, reflection, matching normalized hashes, method metadata and guard source manifest. The host gate requires exactly four and sixteen distinct certificates, matching the saved independent tiny oracle sets in evidence SHA-256 `3bc2773387fe320e440bbc6a02a5b53dc4952bf17bd31ecb75ebb94b6789ec7a`. Those additional tiny driver verifications and checkpoint identity checks are outside each guard's RSS measurement; their time is included in the driver summary's elapsed interval. The gate driver never invokes a census, model search or numerical oracle to derive expectations.

Witness callback order is not observable in the unchanged guard's hash-named witness files. This host gate therefore checks counts and distinct witness sets only, and records `witness_order_observed=false`. Witness order remains supported by the existing source/tiny core tests. Sorting certificate hashes in the gate summary is only a presentation order, not evidence of traversal order. Root explicitly selected this narrow two-launch design rather than adding callbacks or a long one-node host continuation sequence.

A separate n5 cancellation case copies the retained accepted one-node checkpoint bytes and exact digest into a new test path, then launches the standalone guard once. The driver observes a direct child whose command identifies the actual private worker before sending SIGTERM to its own live supervisor child. It requires supervisor exit 2, cancelled supervisor/helper reports, clean helper cleanup, positive samples, no accepted or published checkpoint promotion, byte-identical predecessor checkpoint, and absence of the observed worker PID after supervisor exit. The driver never signals the cached worker PID; only the unchanged helper may clean its verified owned process group. An observation race, permission failure, missing report, zero samples or uncertain cleanup fails the gate. No sleep is inserted to keep the worker alive and no automatic retry hides a missed observation.

The driver preserves commands, stdout/stderr, reports, checkpoint snapshots, certificate hashes and verifier results, cancellation PID evidence and a final summary in a new output directory. Its required out-of-band expected-script hash is checked before work and again before success. The complete source manifest and saved-oracle hash are also checked before and after. Timeout cleanup first terminates the directly owned supervisor; if it remains, the driver may kill that direct child, marks ownership unknown and requires a separate audit. No such outcome is success or permission for continuation.
