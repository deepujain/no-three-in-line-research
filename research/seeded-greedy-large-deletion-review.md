# Seeded greedy large-deletion exploration review

Reviewed existing `src/search.py` SHA-256 `0e132a360bdb1408fdf5b3ebebeb1b37650177c421e5d2fe8ae32c35502ae123` and its focused tests without running a numerical experiment. Its initial-certificate branch independently verifies the published 156-point input, embeds it in n79, tries direct additions once, then samples between one and the specified maximum number of deletions uniformly per repair pass. It shuffles all vacant cells and greedily adds a point only when no pair of retained points is collinear with it. Only strictly larger valid sets replace the incumbent; the final certificate is checked by both integer verifiers. It can sample neighborhoods beyond five deletions, but does not record deletion-size history, accept equal-size neutral moves, or certify completeness. A maximum of 12 does not prove a particular run actually sampled six or more deletions. Existing tests and recorded smoke runs support basic behavior but do not establish n79 yield or performance.

A bounded exploratory candidate is seed 279106, 25 search-loop seconds, `--delete-count 12`, published n78 input (file SHA-256 `4c13bf3e807885f9e61d00593bb27d060b773e40d887f63d955d962d9890a912`), and a fresh output path. This is a stochastic probe, not an exact six-deletion census or a repeat of a closed five-deletion enumeration. A valid 157- or 158-point output passing both verifiers improves the local 156-point incumbent; normalized hash and literature must be checked independently before any novelty or priority claim. An unchanged 156-point output or timeout establishes no impossibility. The program reports candidate evaluations and passes, not unique configurations or tested deletion sizes.

The existing experiment pool does not allow `src/search.py`; this CLI has no standalone owned-process RSS guard. Setup, final dual audit and file write can exceed its search-loop time, and it only writes at the end, so abrupt termination can lose an improvement. The existing owned-process helper caps each invocation at 30 seconds; a 25-second search-loop budget under a 30-second helper allows at most five seconds of tail, which is not guaranteed to suffice. The proposed 65-second helper setting was invalid and rejected before spawning a worker. Source pins, clean exit/cleanup and independent final verification are required before accepting a result; do not silently add it to the frozen dispatcher. Preserve the valid input and run once without retry or inflated caps. An alternative already independently reviewed and pool-allowlisted `src/trade_search.py` can change many seed points through invalid full-state trades, but prior score-11 rectangle neighborhoods and annealing did not improve, and it is not the requested deletion/greedy-repair method.
