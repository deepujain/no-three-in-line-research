# Proposed bounded checkpointed diagonal DFS trial

Design only; do not schedule until independent approval of the exact guard and dispatcher sources, real-host n=3 and n=5 CLI initial/resume gates, and a Lead allocation. The unchanged 30-second and 256-MiB sampled owned-process gate includes setup and cleanup; it is not a hard instantaneous RSS ceiling. This proposal does not authorize a run or imply a performance outcome.

The first trial uses n=79, deficit `d=0`, diagonal singleton `t=0`, the same restricted slice as r24, and a 1,000-node limit. r24 reached 100 nodes in 0.115219 worker seconds, with 55,552 KiB sampled peak and no witness; those measurements motivate a small 10-fold node cap but do not predict this checkpoint wrapper's time, memory, or total slice size. Since r24 had no frontier, the initial checkpointed invocation necessarily retraces its prefix. Use fresh paths `data/diagonal-checkpoint-trial-frontier.json` and `data/diagonal-checkpoint-trial-01-report.json`; reject existing files rather than silently reusing them. The unique witness directory is recorded in the report.

After the first invocation exits and the Lead independently verifies its receipt, helper `gate_status=exited`, `cleanup_status=clean`, source stability, expected source/model/order hashes, accepted checkpoint digest and report/frontier agreement, run one further 1,000-node invocation using the same checkpoint, a distinct report `data/diagonal-checkpoint-trial-02-report.json`, and `--expected-sha256` set to the accepted digest from the first verified receipt. Acquire the checkpoint lock as normal. Do not precompute or guess the resume digest. Queue the second job only after the first terminal receipt is accepted; this two-job trial has at most 2,000 newly counted nodes and is not an indefinite chain.

Stop the chain if either invocation has an external wall, RSS, monitor, cleanup, source or cancellation failure, lacks an accepted digest, changes expected source identity, fails checkpoint/hash verification, exhausts its slice, or needs recovery after interrupted publication. Do not advance a node-limited frontier on an untrusted report. If the checkpoint was promoted but final receipt was interrupted, inspect the incomplete report, checkpoint content and predecessor hash, then require an explicit trusted recovery decision and newly pinned digest; a predecessor field alone is not authentication. Any saved witness must be checked independently using both geometry verifiers and reflection/count checks before reporting, with novelty left unclaimed.

A node limit or timeout is incomplete. Even genuine exhaustion applies only to the declared `(0,0)` diagonal-reflection slice; it does not establish infeasibility for the other diagonal-reflection slices, other symmetries, or unrestricted configurations. The checkpoint source, fast core, verifier, helper, guard and exact final dispatcher hash must be frozen and bound consistently for both invocations. The checkpoint identity binds core and verifier sources; the two guarded reports separately bind the helper, guard and dispatcher. Compare those report hashes explicitly between stages: a change requires separate review and must not be silently resumed as the same trial.
