# Guarded checkpointed diagonal DFS

The separate `--diagonal-secant-checkpoint-guard` route uses the owned-process helper with at most 30 seconds and 256 MiB sampled guard-plus-owned-process RSS. It reserves the greater of one second or one quarter of remaining time for cooperative checkpoint publication and cleanup, while the external guard applies the remaining overall budget. This is a sampled gate, not a hard memory cap; process monitoring and cleanup can overrun the nominal wall deadline. Historical search and guard sources remain unchanged.

An exclusive nonblocking flock on the checkpoint's `.lock` file covers the entire invocation. Resumes require an externally trusted expected hash. A worker operates on a private staged copy, verifies both geometry checkers before atomically publishing hash-named witnesses, and atomically writes its staged frontier and result. After a clean helper exit the parent rechecks source stability, checkpoint/result digest, full configuration, orbit ordering and source identity, predecessor digest, counters, and completed frontier before atomically promoting the checkpoint. A monitor, resource, cleanup, source, or cancellation failure prevents a completion claim. If a cutoff, cancellation or source change is detected after promotion or during finalization, the accepted hash is null and the report separately identifies the published but unaccepted checkpoint bytes. Never automatically adopt those bytes for coverage. The initial report names a unique witness directory even if no frontier is accepted.

If execution stops before promotion, the previous accepted checkpoint is untouched and the invocation can be replayed; already emitted witnesses remain valid and are idempotently named. If it stops after promotion but before the final report, the initial report stays incomplete and the new checkpoint contains the expected predecessor hash. The owner must inspect the locally trusted checkpoint, validate its identity and predecessor, and explicitly pin its new byte digest for recovery; a predecessor link alone cannot authenticate arbitrary substituted bytes. The helper monitors the worker and its cleanup; the parent checks timing, cancellation and sources through promotion and after the first terminal report write. The final corrective receipt write, lock release and return remain a cooperative tail; there is no hard deadline guarantee. Both checkpoint and report files are fsynced before atomic replacement, but their parent directories are not fsynced; no power-loss durability is claimed. A trusted hash and cooperating users of the same lock are necessary; an uncooperative writer can bypass flock.

The combined test command for checkpoint guard/core, owned helper, fast guard and existing SAT tests passed 55 tests. Tiny n=3 and n=5 slice/resume and CLI tests use real DFS subprocesses with the resource helper mocked; they cover trusted hashes, identity mismatches, witness validation, lock contention, cancellation forwarding, post-worker guard failures, and interruption before and after promotion. The helper has separate tests and real-host validation; this adapter still requires independent review and real-host tiny CLI checks. No n=79 work or benchmark was run.
