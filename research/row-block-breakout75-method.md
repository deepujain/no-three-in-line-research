## Fixed experiment and exact arithmetic

The CLI fixes n75,149 points, local RNG seed275149,200000 transitions maximum, migration every16th transition with32 samples, and a penalty update at32 global-best-stagnant transitions. Nondefault line weights are capped at65536 keys and65535 per value. It reads no published geometry source and imposes no symmetry or column-capacity restriction. Hard row loads remain one singleton and74 pairs; deficiency migration changes which row is single. A zero exact geometry score implies the soft column constraints also hold, but only two independent full validators establish a witness.

Canonical primitive line keys are `(a,b,c)` for ax+by=c with first nonzero normal coordinate positive. Pair-index values are149-bit membership masks; there are at most11026 keys. Full scores sum C(t,3), preserving every triple on long lines. Emptying a row permits exact unary costs w*C(t,2) at its lattice intersections; replacing a pair is the sum of its two unary costs. Every alternative except the current row set is considered, and uniformly selected minimum-cost ties may force an uphill move. Migration has a separate sequential removal/insertion calculation and never applies same-row additivity across two rows. Every chosen next state is independently rescored by rebuilding its complete pair index; a delta mismatch aborts the transaction.

The meaningful best score is unweighted. Weighted changes from penalties are not geometric improvements. The best state never regresses. Weight penalties are persistent with no eviction. Each due update first checks all bounds, copies the map, applies every increment and recomputes the weighted score before commit. At most current/next indexes and two weight maps coexist. No all-grid line table, tabu history, restart, population, external solver or alternate seed exists.

Pure APIs are `line_key`, `build_index`, `row_costs`, `best_row_alternatives`, `migration_delta`, `make_boundary`, `initial_boundary`, `propose_transition` and `checkpoint_bytes` in `research/row_block_breakout75.py`. `build_index` returns sorted points, index, raw score, weighted score and sorted conflict rows. Row costs return separate raw/weighted arrays. Migrations return separate exact deltas. A frozen `Boundary` holds complete current/best state, index, immutable-by-contract weights, RNG and committed logical counters. All point-mask positions refer to the sorted current points.

## Atomic transitions and shutdown

Selection and RNG draws, complete migration samples, the proposed index/scores, best/stagnation changes and any due complete penalty update are staged. Any precommit deadline, cap or error restores the preceding RNG and retains the preceding boundary, including weights and logical counters. Work counters record the abandoned effort separately. One returned boundary constitutes acceptance. Initial and completed next-state zero indexes bypass optional penalty/telemetry work and receive immediate validation priority.

The at-most25-second soft budget begins before remaining imports. Search stops23 seconds after entry, reserving2 seconds for finalization. Validator one must start within main soft time; validator two starts only if the first finishes in time. A successful second validator is followed by atomic witness publication before optional hash/checkpoint/pin work. Candidate metadata records exact row/column counts computed before validation. Later failures cannot withdraw the saved witness; they invalidate run acceptance. A raw zero checkpoint is labeled `unverified_zero_candidate` until both validators accept that identity.

`completed-boundary.json` is written once at shutdown and never read by the pilot. It contains sorted current/best points, scores, deficient row, sorted `[a,b,c,w]` records, exact Python RNG version3 state, committed counters, policy constants, source/runtime/manifest identities and actual soft/search budgets. The line index is reconstructible and omitted. Score-at-capture fields for the best state are explicitly historical; only its raw score is used as the best objective. Work counters and aborted attempts remain in the report rather than the continuation boundary.

The checkpoint is built and schema/size checked before atomic write/fsync/rename. It has a hard2MiB cap and16KiB metadata cap. Compact weight records need at most1441793 bytes; RNG and both point arrays are small. Report publication records the exact checksum and length. Mandatory bounded serialization/publication may finish after soft time under the30-second owned guard; the final deadline check still rejects run acceptance. A crash may leave no checkpoint or an unaccepted temporary file. No production continuation or import behavior is implemented; future continuation requires a separate allocation and reviewed contract.

At most11026 lines and2775 alternative pairs are scanned in a row step. Each migration samples32 moves and uses at most9536 point-line incidences. These bounded hashes permit review of repeated states across recorded penalty events without claiming a global distinct-state census. It records initial/current/best raw scores, committed row/migration/penalty counters, partial work and monotone weight-key maximum. It never claims family exhaustion: `closure` is always false. `accepted` means an intact completed prefix/checkpoint and final pins/deadline checks, not a construction or complete neighborhood search. A normal search-deadline or named weight cap can end an accepted prefix; missing/incomplete checkpoint, errors, validation failure, source drift or late finalization cannot.

Only bounded point artifacts are retained: initial research state, current/best in the checkpoint, an optional dual-checked best diagnostic, and any valid witness. A positive-score diagnostic is explicitly invalid. Optional best validation is attempted only with remaining finalization time and raw score<=1000, bounding conflict-report allocation; this is an artifact-cost guard, not search pruning. Validator summaries and a matching conflict-list hash are stored instead of large duplicate conflict arrays. Zero witness validation is always prioritized.

The worker requires a reviewed manifest covering itself, `src/verify.py`, the resolved interpreter binary and the resolved stdlib `random.py`, plus Root's chosen design/review/test/runtime sources. The CLI has only output, source-pin and at-most25-second duration options; it has no seed, resume, source, target or policy override.
